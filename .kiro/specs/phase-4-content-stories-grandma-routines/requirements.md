# Requirements Document

## Introduction

Phase 4 gives Xelulu something to say and a day to keep to. It builds, against the Simulator and the Phase 3 mocks: a curated Content_Library of original retellings, songs and learning activities; the Storyteller and interactive branching stories; the mother-tongue Word_Of_The_Day; Grandma mode as metadata plus signalling; a Routine_Scheduler with charge reminders, quiet hours and play limits that fires through the Phase 3 device policy gate; parent-requested Reports computed from real in-process activity; the Admin_Console's Content tab; and the parent app's Play, Grow, Reports and Routines screens reading the real models instead of mock tiles.

Every wave is built behind a store interface with an in-memory implementation, because Phase 5 swaps in a Supabase implementation and there must be no rework: the interface is defined, the memory implementation satisfies it, and every caller depends only on the interface (C1).

The Document B v2 contract does not change. `proto_ver` stays 2, no field is added, no enum is renamed, no new topic appears. Every device action this phase needs already exists in `CMD_ACTIONS`, and `play.data.content_id` already carries a curated content id (C29). The Gateway_Log is not the contract and is versioned separately; this phase adds five entry kinds and moves `GATEWAY_LOG_VERSION` to 3 (C22).

There is still no backend in this repo. Content, consent, Grandma records, routines, activity and reports live in the Gateway's own process, bounded and in memory, and are lost on restart (C1). The parent app does not talk to the Gateway at all: it reads the same shared models and the same Starter_Content through an in-app store interface, with no HTTP, no fetch and no MQTT (C26).

### Out of scope

- The cloned Grandma voice (XL-G06) and any voice cloning. The licence gate stays recorded (F5).
- Any audio byte for a Grandma recording. Phase 4 holds metadata and an opaque Media_Handle only (C11).
- A media transport for the live Grandma call: no WebRTC, no SIP, no RTP, no new socket (C12, F4).
- Supabase: persistence, Row Level Security, roles, parent view/delete/export of content, consent or reports (Phase 5).
- Any real STT, LLM or TTS provider. The Phase 3 mocks stay wired; the Safety Hardening gate (`safety.md` §9) stays open (F8).
- Make-a-story (XL-G03), festivals (XL-G08), announcements (XL-C04), ask-parent questions in the app (XL-C09), reading (XL-L05), science (XL-L06), NFC code cards (XL-L10), homework hints (XL-L11), adaptive difficulty (XL-L12).
- Walkie-talkie (XL-C03) and remote play (XL-M08).
- The remaining eight Indian languages: `en-IN` and `hi-IN` only (Phase 3 C13).
- Authentication on the Operator_Surface, the Control_Surface or the Admin_Console (still open from Phase 1.2 G24/G46, F7).
- Real hardware, OTA, pairing, and any `proto_ver` change.

### Choices made

Each choice was made without asking. Items marked **FLAG** change a steering rule, a prior-phase decision, a protected file or a dependency; approving this spec approves them as written. Rulings that genuinely need Omar are listed separately under "Rulings still needed".

- **C1. FLAG: six in-memory stores behind interfaces, in the Gateway process only.** Content_Store, Consent_Store, Grandma_Store, Routine_Store, Activity_Store and Story_Sessions. Each is defined as a TypeScript interface, implemented in memory, bounded, and reached only through that interface; Phase 5 replaces the implementations with Supabase ones under RLS and changes no caller. All of them are lost on restart. That promise is about the interfaces and their callers and does **not** extend to the one row model C43 holds Gateway-locally: reconciling `GrandmaRecording` with the shared `GrandmaAsset` row is expected Phase 5 work, named rather than claimed to be zero. This extends the Phase 3 C10 no-backend boundary to six more kinds of state rather than loosening it.
- **C2. FLAG: `ContentKind` gains `learning`.** The shared union becomes `story | song | rhyme | lullaby | game | learning`. Phase 2.2's `mock-play.ts` records the workaround this removes ("the union has no learning member, so the three learning cards take `game`"). Additive to the domain model, which is not the contract; `GrandmaAssetKind` is untouched. Blast radius: `packages/shared/src/domain/content-item.ts`, the shared export test's type list, and the Phase 2.2 Play mock's comment and `kind` values.
- **C3. FLAG: `ContentItemBase` gains `status`, `source`, `steps` and `updated_at`.** The Phase 1 row model becomes the row Phase 5's Supabase table will hold, so the model is extended once rather than shadowed by a gateway-only copy. `licence_note` already exists and stays required. Blast radius: the shared domain, the export test's type list, and anything that builds a `ContentItem` literal (today: nothing outside the new Starter_Content). The Grandma row is deliberately **not** treated this way, and C43 says why rather than leaving the asymmetry unexplained.
- **C4. The eight content categories are frozen and are the ones the system already uses.** `stories`, `songs`, `animals`, `maths`, `world`, `feelings`, `manners`, `games` — exactly the keys of the Phase 3 Input_Guard's `CONTENT_CATEGORY_TERMS` and the categories of the Phase 3 content fixture and the Child_Context fixture. They move to one frozen shared constant and a Repo-level test asserts the three lists are equal. A ninth category would be a tool call no household's `allowedCategories` can satisfy — a bug Phase 3 shipped once and this phase must not repeat.
- **C5. Every seeded item is original wording.** Every story, song and activity is written for Xelulu. No existing translation or published text is pasted or lightly edited: Panchatantra, Jataka, Tenali Raman and Akbar-Birbal are old traditions, but modern translations are copyrighted. Each item carries a `licence_note` saying it is an original retelling written for Xelulu, and a `source` naming the tradition only (`panchatantra`, `jataka`, `tenali_raman`, `akbar_birbal`, `folk`, `original`). A test asserts every item has a non-empty licence note and a source from that closed list.
- **C6. The Output_Guard's word lists are a seeding constraint, written down rather than discovered.** `checkOutput` refuses a reply containing a URL, a phone-like number, a price word, a blocked brand, or a romantic, frightening, medical, legal or financial term, and refuses any text outside the Age_Stage's sentence and word limits. So the seeded prose must avoid, among others: `bank` (a river's edge, never a bank), `court` (a king's hall, never a court), `police`, `jail`, `lawyer`, `doctor`, `medicine`, `fever`, `hospital`, `monster`, `ghost`, `witch`, `blood`, `kill`, `murder`, `nightmare`, `kiss`, `price`, `cost`, `buy`, `rupee`, `dollar`, `amazon` (the rainforest is blocked with the shop), and their Hindi equivalents in the same lists. The age tags are a promise about shape: each Content_Step must fit the sentence and word limit of **every** Age_Stage the item declares (`tiny` is 1 sentence and 8 words), which is why a story is a list of short steps rather than one body of prose.
- **C7. The Active-status gate lives in the Content_Store, not in the UI.** An item becomes `active` only if `checkOutput` passes for every spoken field **and for the assembled step utterance** (C39), at every declared Age_Stage and in every declared language. The check is the store's single choke point, so no route, no console control and no seed path can set Active around it — and `create` and `update` never produce `active` at all, whatever their verdict (Req 2.4a). A draft that fails keeps its verdict (rule, Age_Stage, language, step, field) visible for the console to show.
- **C8. Curated text wins over generated text.** When a Story_Session supplies a step, the Turn_Pipeline speaks that step's curated text verbatim and discards the model's reply text for that turn. safety.md §3 says stories and songs come only from the curated library; letting a model paraphrase curated text would make that promise untestable. The Output_Guard still runs on the curated text, so the library is not trusted to police itself either.
- **C9. A branching answer is resolved by word list, not by a model, and the child's words are not kept.** Each Content_Choice carries match terms per language; the child's transcript is matched case-folded against them after the Input_Guard has run. Only the resolved `choice_id` and `step_id` reach a Log_Entry, an Activity_Record or the Story_Session. The answer text itself goes nowhere except the Phase 3 Transcript_Store, which already holds it as text with its 30-day expiry.
- **C10. Word_Of_The_Day is a `learning` item in the `world` category, picked by day index.** `world` is the existing category that covers language and culture, and C4 forbids a ninth. The day's word is `starterWords[dayIndex % count]` on the Gateway's Clock, so the same local day always gives the same **index** for every child, with no per-child state, no history and no preference — nothing that could become a profile (safety.md §2).

  **What "the same word" does and does not mean.** A `WordEntry` carries one `lang`, because a mother-tongue word *is* language-specific: the Hindi word of the day is not a translation of an English one, and XL-G07's promise is a family word, not a shared vocabulary item. So the day's index is identical for every child, and the entry that index resolves to is identical for every child **speaking the same language**; an English turn and a Hindi turn on the same local day may land on different entries, because `wordForDay` walks forward from the shared index to the first entry carrying the turn's language (Requirement 5.5). Making `word`, `meaning` and `example` localised so one entry served everyone was considered and rejected: it would make the day's word a translated pair rather than a mother-tongue word, which is the feature. Requirements 5.2 and 21.6 state the claim at this strength and no stronger.
- **C11. FLAG: no Grandma audio byte exists in Phase 4.** safety.md §1 permits adult-provided Grandma recordings with a recorded consent statement, and Phase 4 does not store one, because there is no storage backend, the audio-retention Repo_Check permits byte-typed values only inside the named Audio_Byte_Modules, and no file-writing API may appear in either service. A Grandma_Recording is therefore metadata only: `asset_id`, `household_id`, `consent_record_id`, `title`, `lang`, `duration_s`, `created_at`, `schedule`, `status`, and an opaque `media_handle` string that no code dereferences. No audio byte is held, decoded, written or streamed; `AUDIO_BYTE_MODULES` is not touched and no byte-holding module is added. Scheduled playback goes through the existing say/play path with a guard-checked narration standing in for the recording. Real stored audio arrives in Phase 5 with Supabase Storage under RLS.
- **C12. FLAG: the live Grandma call is signalling only.** "No new egress" forbids a media plane, so the call is a state machine plus device commands — `request`, `ring`, `accept`, `decline`, `end` — gated by quiet hours and the play limit, with a call record held in memory. No WebRTC, no SIP, no RTP, no new socket, no new dependency, no audio of any kind in either direction. The deferred media transport is recorded as an open item (F4).
- **C13. `voice` stays `xelulu` everywhere.** The contract's `SAY_VOICES` includes `grandma`, and this phase uses it nowhere: a Grandma narration is Xelulu reading an adult-authored title, not a cloned voice, and the `grandma` value belongs to XL-G06 behind its licence gate (F5). This reaffirms Phase 3 C20 rather than changing it.
- **C14. A Grandma_Recording cannot exist without a live Consent_Record.** The Grandma_Store refuses to create one unless `consent_record_id` names a Consent_Record that exists, has purpose `grandma_recording`, belongs to the same household, and has `withdrawn_at` null. Withdrawing consent marks every recording that cites it `withdrawn` and makes it unschedulable and unplayable, because erasure on withdrawal is a DPDP duty (safety.md §2), and in Phase 4 there is nothing to erase but the metadata.
- **C15. The Routine_Scheduler rides the existing Clock and Deadlines.** No new timer source, no `setInterval`, no wall-clock read. Routine times are `HH:MM` in the device's local day, the same shape the contract uses for quiet hours, so nothing reasons about time zones. Every timing test drives it with Vitest fake timers.
- **C16. Every routine, reminder, nap and call command goes through the existing device policy gate.** `services/gateway/src/brain/tools/device-action.ts` is the only path to the command sender for all of them, so quiet hours, the play limit and the movement toggle are checked before anything is sent and there is no second policy path to keep in step. Only the five conversational actions (`say`, `animate`, `gesture`, `led`, `play`) are reachable, and every ack `reason` is final: nothing retries around one.
- **C17. Charge reminders fire once per threshold crossing, with hysteresis.** Thresholds are 20% and 10%, read from the accepted `status.battery_pct`. A threshold arms when the battery is above it by the hysteresis margin, or when `charging` is true, and fires at most once while armed. A battery sitting at 18% produces one reminder, not one per heartbeat.
- **C18. A reached play limit ends with a graceful nap, not a cut-off — and the nap is sent on the crossing, before the ledger closes.** The Nap_Sequence is a `say`, an `animate` with a sleepy expression and an `led` set to a dim `solid`, in that order, each through the gate. No `set_mode` and no `stop_audio`: the five conversational actions are enough, and a mode change is the device's own business.

  **The ordering problem, and the chosen answer.** The Phase 3 gate refuses all five actions with `play_limit` when `playMinutesUsed(deviceId) >= policy.playLimitMinutes` — `>=`, so at the instant the limit is reached the nap itself would be refused and "graceful nap" would be silence that every test ratified by asserting nothing was published. Three fixes were weighed: a lead margin (fires a minute early, so the limit is really `limit - 1`); a named gate exemption that skips the `play_limit` branch (a change to the one module C16 keeps unchanged, and a second policy path to keep in step); and firing on the crossing before the ledger closes. **The crossing is chosen**, because it needs no change to `device-action.ts`, no second policy path and no re-reading of the parent's limit: one accrual function computes the total before and after, requests all three nap actions through the unchanged gate while `playMinutesUsed` still reports the pre-accrual total, and only then records the minutes. The limit is exact, the gate is untouched, and from the moment the ledger closes every ordinary behaviour is refused `play_limit` as before. Requirement 13.2 states the rule and Requirement 21.3 tests both halves: the nap's three actions **were** published at the crossing, and an ordinary behaviour at the same moment was refused.
- **C19. FLAG: quiet hours silence routines and reminders too, and that consequence is recorded rather than hidden.** The Phase 3 gate refuses all five discretionary actions during quiet hours, on the conservative reading that a talking robot is not quiet either. Phase 4 inherits that, so a bedtime routine inside quiet hours, a 10% charge reminder at 2 a.m. and an incoming Grandma call at night are all refused with `policy` and nothing is sent. This widens the open product decision recorded as item 4 of `safety.md` §9 from "a comforting reply" to "every cloud-initiated behaviour"; it stays as built until Omar rules (F3).
- **C20. Reports are computed on request and carry no profiling.** A Report_Summary is counts and simple aggregates over a parent-chosen window — turns, play minutes, play sessions, routines completed, stories heard, words learned, cry moments, and the content categories heard. There is no score, no rank, no prediction, no trait and no personality inference, and no transcript text. Nothing is computed continuously in the background, and no Activity_Record carries a child's words. The pending legal review of reports and cry alerts against DPDP s.9 stays **open** (F1); this spec does not claim it closed.
- **C21. The report arithmetic is one pure shared function.** `summariseActivity(records, window)` lives in `packages/shared` and is called by both the Gateway and the parent app, so the console's numbers and the app's numbers cannot drift and the s.9 posture is testable in one place. It is pure: no clock read, no I/O, no randomness.
- **C22. FLAG: `GATEWAY_LOG_VERSION` 2 → 3, purely additive.** Five new kinds: `routine_fired`, `content_gate`, `grandma_event`, `story_step`, `report_built`. No existing kind is removed and no field of an existing kind changes, so an entry built for version 2 differs only in `log_ver`. Blast radius, each handled in tasks: `packages/shared/src/gateway-log/constants.ts` and `entries.ts`; `packages/shared/test/exports.test.ts` (runtime-export count, type list, version assertion); every golden fixture and test that asserts `log_ver: 2`; `apps/admin/src/log/entry-label.ts`, whose `switch` ends in a `never` default and will not compile until the five kinds are handled; the console's kind filter, which reads `GATEWAY_LOG_KINDS` and needs no change; and `tooling/compose/compose-acceptance.ts` with its test.
- **C23. FLAG: the Operator_Surface gains content and Grandma routes, and the write routes are flag-gated. This supersedes a standing invariant.** Phase 1.3 Requirement 8.2 and Phase 3 Requirement 20.6 say the Admin_Console sends nothing but `GET /v1/stream`. Wave 6 needs writes, so: the loopback-only Operator_Surface gains read routes and write routes behind its **unchanged** request guard (Local_Mode only, loopback `Host` only, 403 on a foreign `Host`, 403 on any `Origin`, 404 on an unknown route, 405 on a wrong method, 415 on a non-JSON POST), and every **write** route additionally refuses with 403 `content_admin_disabled` unless the Gateway was started with a new off-by-default `--content-admin` argument, exactly mirroring the proven `--operator-transcripts` pattern in `services/gateway/src/listen-host.ts`. Reads stay available without the flag. The store-level gate of C7 is what keeps this safe: the worst a reachable write can do is add a draft that cannot be activated. The tests that pin the old rule are updated, not deleted.
- **C24. FLAG: the Dev_Proxy forwards the write routes only in the console's content-admin mode.** `apps/admin/vite.config.ts` already loads exactly one non-secret value; it gains no second one. The switch is Vite's own `--mode`: `pnpm dev:admin` forwards the read routes and the stream, and `pnpm dev:admin:content` (`vite --mode content-admin`) also forwards the write routes. A new Panel_Key was rejected because `.env.example` and `tooling/fixtures/approved-panel.txt` are frozen at 23 keys; parsing `process.argv` in the Vite config was rejected because an unknown CLI flag is not a contract Vite offers. The console also hides its write controls when `GET /v1/content` reports `write_enabled` false, so a disabled surface shows no button that would 403.
- **C25. FLAG: Compose adds `--content-admin` to the gateway command.** `docker-compose.yml`'s gateway `command` becomes `["node", "dist/index.js", "--listen-all-interfaces", "--operator-transcripts", "--content-admin"]`, so the manual walkthrough can add a Grandma recording and activate a story. Local development only, published on host loopback only, on an internal console. Supersedes Phase 3 Requirement 18.8's exact `command` array and the exact-`command` assertion in `tooling/test/compose-static.test.ts`.
- **C26. The parent app does not talk to the Gateway.** structure.md is categorical: the parent app only ever talks to Supabase over HTTPS and Realtime, and device commands go app → Supabase → gateway → MQTT. There is no backend in Phase 4, so "wiring the app's screens to the real content, routines and reports" means the shared models and the shared Starter_Content, read through an in-app store interface. No `fetch`, no `XMLHttpRequest`, no `WebSocket`, no `EventSource`, no MQTT, no Supabase client and no new egress; Phase 5 swaps the in-app store implementation for Supabase and changes no screen.
- **C27. FLAG: the parent app may import frozen constants from `@xelulu/shared`, not types only.** Phase 2.1 Requirement 8.3 and Phase 2.2 Requirement 22.3 allow `import type` only, which no shared fixture can satisfy. The rule narrows to the Admin_Console's wording — types and frozen constants — and is enforced by a named allow-list in `tooling/test/placeholder.test.ts`: only the In_App_Store modules may import a value, and only the Starter_Content names the design lists. The assertion is updated, not deleted, and every other file in the app keeps `import type` only.
- **C28. FLAG: one new shared folder, `packages/shared/src/starter-content/`.** It holds the seeded Content_Items, the routine templates and the Word_Of_The_Day entries, and it must be shared because the Gateway seeds its store from it and the parent app reads it, and services may not import each other and nothing may import from `apps/` or `services/`. `.kiro/steering/structure.md` gains exactly one line inside the `packages/shared/` block, as Phase 3 C6 did for `src/mock-audio/`. The Gateway's new folders (`src/content/`, `src/grandma/`, `src/routines/`, `src/reports/`, `src/brain/story/`) need no steering line: that block is already illustrative and does not list `src/operator/` or `src/log/`.
- **C29. No Document B change, and none is expected.** Every action this phase sends is already in `CMD_ACTIONS`; `play.data` already carries `content_id` and `source`; `say.data.lang` already accepts both languages; quiet hours already travel on `config`. No field is invented, no enum renamed, no topic added, and `proto_ver` stays 2. If an implementation step appears to need a contract change it stops and records a blocking question instead (F6 is the slot for it).
- **C30. A cloud-initiated `say` has no audio plane in Phase 4, and that boundary is stated rather than papered over.** The audio WebSocket is per-turn and the device opens it, so a routine, a reminder or a Grandma playback cannot stream audio down it. What Phase 4 builds is the decision, the guard-checked narration text, the command, and the ack handling; the Simulator answers `accepted` then `done` to a `say` outside a turn, which is what the tests assert. The device opening a turn in response to a `say` is Phase 6 firmware behaviour.
- **C31. No new dependency, no new egress, no new file write.** Every manifest's dependency list is unchanged. No `fetch`, no network-module import under `services/gateway/src/brain/`, no transport folder added to either service, no file-writing API in either service, and no vendor SDK. The existing Repo_Checks prove each part and are not weakened.
- **C32. Testing depth: properties where the invariant is universal, examples elsewhere.** Ten named properties (Properties 1–10 in the design) run under fast-check at 100 iterations or more for shared, gateway and simulator code. Admin_Console and parent-app tests stay smoke plus key-interaction only. Every timing test drives the existing Clock and Deadlines through Vitest fake timers; no test waits on wall-clock time.
- **C33. The Admin_Console gains one page and stays otherwise unchanged.** A Content page with a labelled section filter (Stories, Games, Songs, Learning, Grandma), a semantic table, an add and edit form, Active/Draft controls, the refusal verdict as text, and the Grandma list with its consent and schedule state. It reuses the existing shell, state and table patterns, adds no dependency, keeps the Phase 1.3 accessibility bar (semantic elements, labelled controls, 44 pt targets, visible focus, status as text and never colour alone, contrast pairs), and contains no animation, transition or flashing.
- **C34. FLAG: the `household_id` is one in-process constant, resolved from the registered device and never from a request.** tech.md binds a `device_id` to exactly one `household_id`, but nothing in the Gateway holds a household today: the Device_Registry is `createRegistry({ deviceId, token })` with per-device predicates only, Phase 2.2 deliberately dropped `householdId` from its mocks, and `.env.example` is frozen at 23 keys so a new Panel_Key is out. Phase 4 therefore adds `services/gateway/src/grandma/household.ts` holding `DEV_HOUSEHOLD_ID` and `householdForDevice(deviceId, registry)`, which answers that constant for a registered device and null for anything else. The Registry's interface, `createRegistry`'s argument and `registry.test.ts` are **not** changed: putting a household on the Registry would be a wider blast radius for a value that is one constant until Supabase holds the real binding under RLS in Phase 5. Every household-scoped call — `ConsentStore.list`, `isLiveFor`, `GrandmaStore.recordings`, the `other_household` refusal — takes its household from that function, and a request body naming a `household_id` is refused (Requirement 7.9).
- **C35. FLAG: `ReplyTarget` gains one number, `audioStartMs`.** Requirement 13.1 accrues a turn's play minutes from the turn's `audio_start` to its reply ending, and the Gateway has no such instant in the brain: `startTurnLatency` begins at `audio_end` by design, because it measures the latency product.md names. Rather than silently narrowing the accrual window to the part the brain can see, the one place that knows the accepted `audio_start` records it. `services/gateway/src/audio/audio-turn.ts` already runs `messageIn("audio_start")` with the Clock in scope and builds the target in `replyTarget(id)`, so it captures `clock.now()` there and puts it on the target. Additive and read-only; nothing else about the audio path moves. Blast radius, all three sites handled in tasks: `src/brain/turn-responder.ts` (the `ReplyTarget` interface), `src/audio/audio-turn.ts` (the capture and the one construction site) and `test/support/brain-harness.ts` (the one test double).
- **C36. Three closed domain lists become frozen runtime arrays.** `ConsentPurpose`, `VerificationMethod` and `GrandmaAssetKind` are type-only unions today, and Requirements 6.2 and 7.7 require a store to refuse a value outside them — which no runtime code can do against a type. `CONSENT_PURPOSES`, `VERIFICATION_METHODS` and `GRANDMA_ASSET_KINDS` are added as frozen arrays with their unions **derived from them**, so every union stays byte-identical and no existing caller or `import type` moves. Restating the lists inside the Gateway was rejected: a closed domain list copied outside `packages/shared` is a list that can drift. This takes the phase's new runtime exports from 20 to 23 and the export test's count from 176 to 199 (Requirement 20.5).
- **C37. The 20% charge reminder carries a `gesture` and the 10% one carries none.** `gesture` is the only movement-bearing action (`MOVEMENT_ACTIONS` in `device-action.ts`), and Requirement 11.5 forbids a movement-bearing action in the 10% behaviour because a nearly flat robot must not be asked to move. If neither reminder carried one, Requirement 12.7's movement-off case for a charge reminder would be vacuous — a test that can never fail. So `battery_20` carries one small `gesture` (a nudge) after its `say`, which is both a reasonable behaviour at 20% and what gives the reminder a real movement-off case.
- **C38. FLAG: the Word_Of_The_Day is gated by the parent's `allowedCategories` on both paths, and `world` joins the one non-restrictive fixture child.** C10 puts the day's word in the `world` category, and `FIXTURE_CHILDREN.child_mock_1` — the child every Compose criterion and manual step runs under — opens `stories, songs, animals, games, feelings, manners` but **not** `world`. Left alone, that is a contradiction rather than a choice: either the turn path is permanently `not_allowed` for the only usable fixture child, or the morning routine speaks a word the parent's settings would have refused, because a scheduled behaviour never consults `allowedCategories`. Two answers were weighed. Treating a mother-tongue word as a language feature outside the category gate was rejected: safety.md §4 ties what is spoken to the parent's content categories, and a feature that quietly sits outside that gate is the less conservative option (safety.md §8). So **the gate applies on both paths** — a word-of-the-day `content_lookup` is refused `not_allowed` when `world` is closed, and the `morning` behaviour falls back to a plain greeting for the same context (Requirement 5.4b) — and `world` is added to `child_mock_1` so the feature is reachable where it is demonstrated. That fixture line is the only interface- and rule-level change: no interface, no rule and no other child moves.

  **The consequence this fixture line does have, stated rather than left to be discovered.** It moves a safety verdict for the Simulator's `scary-request` utterance under the one child everything runs as. Read on this tree, `checkInput` has **no** frightening-content rule at all: its precedence is `harm_disclosure → distress → defer_topic → blocked_category → too_long → uncertain → allow`. `scary-request`'s text — `"will the volcano hurt the cat"` — carries no first-person anchor and no `my`, so neither `disclosesHarm` nor `isDistressed` fires; the **only** reason that utterance refuses for `child_mock_1` today is that `world` is closed and `volcano` is a `world` term (`CONTENT_CATEGORY_TERMS.world`). Adding `world` therefore makes `scary-request` an **`allow`** turn for `child_mock_1`. So that utterance never demonstrated input-side frightening-content refusal in the first place — it demonstrated a blocked-category refusal, and its own header comment in `services/simulator/src/audio/test-utterances.ts` ("a frightening request → refuse, a Safe_Redirect") was already describing something the code does not do. No test goes red either way, because every `input-guard`, `tool-router`, `turn-pipeline` and `output-guard` test builds its own context and none pins that child's category list.

  Three things follow, all of them in this spec rather than left as a silent change: the header comment and every spec table that describes `scary-request` are corrected to say what it actually demonstrates (Requirement 22.1b); a **thirteenth** Test_Utterance, `closed-category-request`, is added through the one category `child_mock_1` still has closed after this line — `maths`, whose `CONTENT_CATEGORY_TERMS.maths` holds `"count to"` — so the live stack keeps a reachable input-refusal demonstration (Requirement 22.1c); and one test pins the intended Safety_Decision for **every** Test_Utterance under `FIXTURE_CHILDREN.child_mock_1`, so the next permissive fixture edit turns a test red instead of silently deleting a demonstration (Requirement 22.6). The Phase 3 manual checklist's step 7 reads `scary-request` as its refusal demonstration; the replacement is `closed-category-request`, recorded here rather than by editing the closed Phase 3 spec.
- **C39. A branching step is measured as one assembled utterance, which decides how many choices and which Age_Stages a branching item can have.** The Content_Gate measures `stepSpeech(step, lang)` — text followed by prompts — as well as each field on its own, because Requirement 4.1 is about the assembled utterance and per-field checks cannot bound it. The arithmetic then settles two things that would otherwise be judgement calls: a branching step costs at least three sentences (one of text, one per prompt), so a branching Content_Item declares `explorer` and `maker` only, and the operative choice count on a spoken step is **two** while `CONTENT_MAX_CHOICES_PER_STEP` stays 3 as a structural ceiling. `tiny` and `little` get linear stories, which is also the right product answer: a one- or two-year-old is not making branch decisions.
- **C40. The Tool_Router opens the Story_Session; the Content_Library only resolves.** The seam needs an owner, and only one module holds both halves. `ContentQuery` carries no `device_id` and no `turn_id`, so `content-library.ts` cannot start a session or register a pending utterance even in principle; the Tool_Router has the `ToolTurn`. So the library answers a start request with the resolved `ContentItem` and a word-of-the-day request with the `WordEntry`, and the router calls `StorySessions.start({ deviceId, turnId, item, lang })`, which opens the session **and** registers the turn's pending curated utterance in one call so the story path cannot forget the second half. `createContentLibrary` therefore takes no `StorySessions` dependency at all. The router's tool-result text for a started story or a word is a fixed constant, never the curated prose, so nothing curated enters a provider prompt (C8).
- **C41. A Grandma title is gated at write time, and the `tiny` narration names no title.** A title is operator-submitted free text that goes into spoken narration, and the Content_Gate covers Content_Items only — so without a check a title naming a doctor or blood is stored, scheduled and then silently unplayable. The Grandma_Store therefore runs `checkOutput` on the narration built from the title at write time, for every title-naming Age_Stage and both languages, and refuses `gate_refused`. The `tiny` narration names no title, because one sentence of eight words cannot reliably hold a template plus a free-text title and the alternative — a four-word title cap — would make the feature unusable for the adult writing it. The runtime check of Requirement 8.3 stays as the belt to that braces, with the Requirement 8.3a fallback written out rather than left to judgement.
- **C42. Every device-facing value in the payload table stays inside the contract's published vocabularies, and no new one is invented.** `say.expression`, `animate.expression`, `animate.eyes` and `gesture.name` are `nonEmpty` strings in Document B, so a new value would be schema-valid and would not be a `proto_ver` change — which is exactly why the choice needs recording rather than making. These are **hardware-facing** values: product.md makes every hardware-facing choice CTO-decided and final, with the Phase 6 firmware built to match our contract, so seven new names chosen inside a payload table would create a firmware obligation nobody agreed to, for behaviours a child never sees this phase. The design's payloads therefore draw only on `KNOWN_EXPRESSIONS` (`happy`, `love`, `sleepy`, `curious`, `sad`, `listening` — of which this phase uses `happy`, `sleepy` and `love`), `KNOWN_EYES` (`blink`, `hearts`) and `KNOWN_GESTURE_NAMES` (`wave`, `high_five`, `hug`, `clap`, `point_left`, `nod`, `shake` — of which this phase uses `wave` and `nod`). An earlier draft invented seven: `excited` and `calm` for `expression`, `open`/`sleepy`/`smile`/`wide` for `eyes`, and `nudge` for the `battery_20` gesture; each is replaced by a published value in the payload table, with `ANIMATE_EYES` reduced to the two `KNOWN_EYES` members and `battery_20`'s gesture becoming `nod` (any gesture name serves Requirement 12.7, which gates by **action** and not by name). `KNOWN_EXPRESSIONS`, `KNOWN_EYES`, `KNOWN_GESTURE_NAMES` and every contract file are **not** touched. Widening a vocabulary is a Phase 6 conversation with the firmware side, not a Phase 4 payload-table decision.
- **C43. The Grandma row is held Gateway-locally this phase, unlike the Content row.** `packages/shared/src/domain/grandma-asset.ts` already holds a Grandma row — `asset_id`, `household_id`, `recorded_by_user_id`, `kind`, `title`, `lang`, `recording_storage_path`, `consent_record_id`, `created_at` — and C3 makes the opposite call for `ContentItem`, extending the shared row rather than shadowing it. The asymmetry is deliberate and is recorded here rather than left unexplained: `recording_storage_path` is a **storage path**, and Requirement 7.2 forbids one until there is storage to point at (C11), so extending the shared row now would bake a field into the row Phase 5's Supabase table will hold that this phase must never populate. `GrandmaRecording` is therefore the Gateway's own row behind `GrandmaStore`, with `GRANDMA_ASSET_KINDS` still shared (C36) so the `kind` list cannot drift. **Phase 5 reconciles the two shapes when Supabase Storage exists under RLS, and that reconciliation is named here as expected work rather than claimed to be zero** — C1's "no rework" promise is about the store interfaces and their callers, and it does not extend to this one row model.

## Requirements

### Requirement 1: The content model and the starter library

**User Story:** As Omar, I want one curated library model that the robot, the console and the app all read, so that nothing a child hears comes from two places.

#### Acceptance Criteria

1. THE Shared_Package SHALL define a Content_Item carrying `content_id`, `household_id` (null for a curated row), `kind`, `title`, `languages`, `age_stages`, `categories`, `steps`, `status`, `licence_note`, `source`, `created_at` and `updated_at`, and SHALL export the frozen lists `CONTENT_KINDS`, `CONTENT_STATUSES`, `CONTENT_CATEGORIES` and `CONTENT_SOURCES`. (C2, C3, C4.)
2. THE Shared_Package SHALL define a Content_Step carrying `step_id`, the step's text per Supported_Lang, its Content_Choices and its `next_step_id` (null ends the item), and a Content_Choice carrying `choice_id`, its prompt per Supported_Lang, its match terms per Supported_Lang and its `next_step_id`.
3. THE `CONTENT_CATEGORIES` list SHALL equal the Phase 3 Input_Guard's `GATED_CONTENT_CATEGORIES`, and a test SHALL fail if the two lists differ in membership or order. (C4.)
4. THE Starter_Content SHALL provide at least two Panchatantra, two Jataka, two Tenali Raman and two Akbar-Birbal retellings, at least three songs, and at least one learning activity in each of `animals`, `maths`, `world`, `feelings` and `manners`, with at least one item in `games`. THAT `games` item SHALL carry `games` as its **only** category, which is the seeding rule Requirement 19.3 relies on so the Play screen's fixed-order category map files it under `Games`.
5. THE Starter_Content SHALL include `hi-IN` text for at least one item of each tradition and at least one song, and SHALL carry every declared language's text on every step of every item it declares that language for.
6. EVERY Starter_Content item SHALL carry a non-empty `licence_note` stating that it is an original retelling written for Xelulu, and a `source` from `CONTENT_SOURCES` naming the tradition only. (C5.)
7. EVERY Starter_Content item's `categories` SHALL be a non-empty subset of `CONTENT_CATEGORIES`, and its `age_stages` SHALL be a non-empty subset of `AGE_STAGES`. (C4, C6.)
8. EVERY Starter_Content item's steps SHALL form a reachable graph: every `next_step_id` and every choice's `next_step_id` SHALL name a step of that item, every step SHALL be reachable from the first step, and at least one path SHALL end with `next_step_id` null and no choices.
9. THE Starter_Content SHALL be exposed as factory functions that return a fresh array per call, so that neither the Gateway's store nor the parent app's store can mutate the other's copy.
10. THE Starter_Content SHALL contain no URL, no phone-like number, no price, no brand name, no digits beside a currency symbol, no child's name and no transcript. (safety.md §3; Phase 2.2 Req 19.5's rule, applied to shared fixtures.)

### Requirement 2: The content store and the active-status gate

**User Story:** As a parent, I want nothing to reach my child's ears unless the safety layer has passed it, so that an editing mistake cannot become something spoken.

#### Acceptance Criteria

1. THE Gateway SHALL define a Content_Store interface with list, get, create, update and set-status operations, SHALL implement it in memory seeded from the Starter_Content, and no caller SHALL depend on the implementation. (C1.)
2. WHEN a Content_Item is created, updated or set to `active`, THE Content_Gate SHALL run `checkOutput`, once per declared Age_Stage and per declared language, on **both** of the following, in this order:
   - **each spoken field on its own** — the item's `title`, each step's text, and each choice prompt — so that a Gate_Verdict can name the offending field (`title`, `text` or `prompt`) and its step; and
   - **the assembled step utterance** `stepSpeech(step, lang)` — the step text followed by that step's choice prompts, which is the exact string the Turn_Pipeline speaks — recorded under the field name `speech`.

   Per-field checking alone cannot satisfy Requirement 4.1, because three short fields that each pass can assemble into an utterance over the Age_Stage's sentence limit; assembled checking alone cannot name a field. Both run, and the gate returns the first refusal (C7, C39).
2a. THE `title` SHALL be inside the Content_Gate, and not merely length-capped. A title is listed in the Admin_Console and is returned to a provider as `content_lookup` tool-result text whenever the lookup lists titles, so it is text that leaves the store; nothing else in the system bounds or scans it. A title carries no sentence terminator, which `sentenceCount` counts as one sentence, so the effective bound on a title is the narrowest declared stage's word limit (eight words at `tiny`) and a title naming a guard term is refused with that rule.
3. IF any Content_Gate check returns a decision other than `allow`, THEN THE Content_Store SHALL leave or set that item's status to `draft`, SHALL record a Gate_Verdict holding the refusing Safety_Rule, Age_Stage, language, step id and field name, and SHALL return a refusal naming them.
4. THE Content_Store SHALL set an item's status to `active` only through the Content_Gate, and no other operation, route, console control or seed path SHALL set `active`. (C7.)
4a. THE Content_Store's `create` and `update` SHALL always produce an item whose status is `draft`, **whatever the Gate_Verdict**; only `setStatus` SHALL ever produce `active`. The seed path of Requirement 2.5 is deliberately not `create`: it is the store's own construction, it runs the same gate, and it is the one path that may land an item `active` without a `setStatus` call. A test SHALL assert that a `create` whose draft **passes** the gate is still `draft`, because that assertion is the whole of C23's "the worst a reachable write can do is add a draft that cannot be activated".
5. WHEN the Content_Store seeds the Starter_Content, THE Content_Store SHALL run the Content_Gate on every seeded item, SHALL hold a passing item as `active` and a failing item as `draft` with its Gate_Verdict, and THE Gateway SHALL add one `content_gate` Log_Entry per seeded item.
6. THE Content_Store SHALL hold its items in memory only, SHALL write to no file, SHALL perform no network call, and SHALL lose everything on restart. (C1.)
7. THE Content_Store's list operation SHALL support filtering by kind, by category, by status, by language and by Age_Stage, and SHALL return items ordered by `created_at` ascending and, for equal `created_at`, by `content_id` ascending — a total order, so two calls on an unchanged store return the identical sequence.
8. THE Content_Store SHALL refuse a create or update whose `content_id` is empty or not unique, whose `categories` are not a subset of `CONTENT_CATEGORIES`, whose `age_stages` are not a subset of `AGE_STAGES`, whose `languages` are not a subset of `SUPPORTED_LANGS`, whose `source` is outside `CONTENT_SOURCES`, whose `licence_note` is empty, whose steps do not satisfy Requirement 1.8, or whose title, step count, step text, choice count, choice prompt, match-term count or match-term length exceeds the named cap the design gives each of them, and SHALL name the offending field path without echoing its value.
9. THE Content_Store SHALL hold at most the design's capacity of items and SHALL refuse a create past it rather than dropping an existing item.
10. THE Content_Store SHALL run every Requirement 2.8 field check **before** the Content_Gate, so that an oversize or malformed draft is refused without the guard scanning its text. (safety.md §9 item 6: the guard's cost grows with input size, so a bound before the scan is the mitigation available to this phase.)
11. THE Content_Store's validation SHALL be the same code on the seed path and on the route path, so a seeded item and a submitted draft cannot be held to different rules; only the caps the design marks route-only differ, and those are enforced by the route.

### Requirement 3: The storyteller (XL-G01)

**User Story:** As a child, I want Xelulu to tell me a story, so that story time happens without a screen.

#### Acceptance Criteria

1. WHEN the Tool_Router runs `content_lookup` with a start request for a category, THE Content_Store SHALL return only `active` items whose categories include that category, whose `age_stages` include the active Child_Context's Age_Stage, and whose `languages` include the turn's language, and SHALL return nothing when the parent has not allowed that category. (Phase 3 Req 9.5's gate, unchanged.)
2. WHEN a start request resolves to an item, THE Gateway SHALL open a Story_Session for that device on that item's first step, SHALL replace any Story_Session that device already had, and SHALL add one `story_step` Log_Entry with that `content_id` and `step_id`.
2a. THE module that opens that Story_Session SHALL be the **Tool_Router**, and no other, because it is the only module holding both the resolved item and the turn (C40). Specifically: the Content_Library **resolves** a start request to a Content_Item and never opens a session — it holds no `device_id` and no `turn_id` and so cannot; the Tool_Router's `content_lookup` handler then calls `StorySessions.start({ deviceId: turn.deviceId, turnId: turn.turnId, item, lang })`, which both opens the session and registers the turn's pending curated utterance under that `turn_id` for the Turn_Pipeline's `takePending(turn_id)` to take.
2d. THE language every `content_lookup` decision uses SHALL be **the turn's resolved language**, read as `turn.lang`, and SHALL NOT be re-derived from `ctx.langs[0]`. `ToolTurn` gains `lang: SupportedLang`, populated at the Turn_Pipeline's one tool-loop call site from the language `resolveLang(detected, context)` already resolved for that turn; `contentLookup` reads it for the eligibility filter of Requirement 3.1, for the step text of Requirement 3.3, for the Word_Of_The_Day entry and its narration (Requirements 5.3, 5.5) and for the `lang` the Story_Session is opened with. Re-deriving it was inert in Phase 3, where a lookup only returned a joined title list; in Phase 4 it decides what is **spoken**, and a bilingual Child_Context (`FIXTURE_CHILDREN.child_mock_1` is `["en-IN","hi-IN"]`, and two Simulator utterances reach `content_lookup` in `hi-IN`) would otherwise open a Hindi turn's session with the English first step while the pipeline's later `advance(deviceId, transcript, lang)` passed `hi-IN` — the session's language and the pipeline's disagreeing from the second turn on. `ctx.langs[0]` stays the right source **only where there is genuinely no turn**: the scheduled behaviours and the call announce (Requirements 5.4, 9.5). That is a one-field additive extension of `ToolTurn`, recorded in the extended-additively table, and a test SHALL prove a `hi-IN` turn for `child_mock_1` speaks the Hindi step and resolves a Hindi match term.
2b. THE `ToolResult.text` the Tool_Router returns for a started story, and for a Word_Of_The_Day, SHALL be a **fixed constant** naming no curated prose — because a tool result is a provider-prompt input, and C8's promise is that curated text is spoken verbatim rather than paraphrased. A lookup that only **lists** titles keeps returning the joined titles, which are Content_Gate-checked under Requirement 2.2a.
2c. THE Tool_Router SHALL read the three new arguments narrowly and SHALL log and echo none of them: `start` and `word_of_the_day` are true only on a literal boolean `true`, and `content_id` through the existing string-only `stringArg` helper. (Phase 3's rule that no argument value is ever logged or echoed, unchanged.)
3. WHEN a Story_Session supplies a step, THE Turn_Pipeline SHALL speak that step's curated text for the turn's language verbatim, SHALL discard the model's reply text for that turn, and SHALL still run the Output_Guard on the curated text before any audio is synthesised. (C8.)
4. IF the Output_Guard refuses a curated step, THEN THE Turn_Pipeline SHALL speak the Safe_Redirect, SHALL end the Story_Session, and THE Gateway SHALL add one `safety_decision` Log_Entry with stage `output` and one `story_step` entry with outcome `ended`.
5. THE Gateway SHALL add no step text, no choice prompt and no child answer to any Log_Entry; a `story_step` entry SHALL carry ids, a closed-enum outcome and nothing else. (safety.md §7.)
6. THE Allow_Listed_Tools SHALL stay exactly the Phase 3 five, and THE Content_Store SHALL be reachable from a provider only through `content_lookup`. (Phase 3 C18, unchanged.)
7. WHEN a Story_Session reaches a step with no choices and a null `next_step_id`, THE Gateway SHALL end the session, SHALL add one Activity_Record of kind `story` with that `content_id`, and SHALL add one `story_step` Log_Entry with outcome `ended`.
8. THE Gateway SHALL hold at most one Story_Session per device, SHALL end a session that has been idle longer than the design's timeout on the Clock, and SHALL lose every session on restart.

### Requirement 4: Interactive branching stories (XL-G02)

**User Story:** As a child, I want to choose what happens next, so that the story is mine too.

#### Acceptance Criteria

1. WHEN a Story_Session's current step has choices, THE Turn_Pipeline SHALL speak the step text followed by that step's choice prompts — the single string `stepSpeech(step, lang)` — within the Age_Stage's sentence and word limits.
1a. BECAUSE the prompts count toward that shape, the reachable number of choices on a spoken step follows from the limits and is not a free choice: a step's text is at least one sentence and each prompt is at least one, so a branching step needs at least three sentences and a branching Content_Item SHALL therefore declare `explorer` and `maker` only — never `tiny` (1 sentence) and never `little` (2). `CONTENT_MAX_CHOICES_PER_STEP` stays 3 as a structural ceiling on the data model, and the operative bound is **two** choices on a spoken step, which three sentences is exactly enough for. A branching item declaring `tiny` or `little` is refused `length` by the Content_Gate at that stage, which is the test rather than a judgement call. (C39.)
2. WHEN a turn arrives WHILE a Story_Session is in progress, THE Turn_Pipeline SHALL run the Input_Guard on the transcript first, and SHALL make no LLM call and no tool call for that turn. (safety.md §4; latency.)
3. WHEN the Input_Guard allows the transcript, THE Gateway SHALL resolve it against the current step's Content_Choices by case-folded match-term comparison in the turn's language, and SHALL advance the Story_Session to the matched choice's `next_step_id`. (C9.)
4. IF no match term matches, THEN THE Gateway SHALL count one unresolved answer, SHALL repeat the step's choice prompts once, and SHALL end the Story_Session with outcome `unresolved` on the second unresolved answer in a row.
5. IF the Input_Guard decides `defer`, `comfort` or `refuse` for a turn WHILE a Story_Session is in progress, THEN THE Turn_Pipeline SHALL speak that decision's reply, SHALL leave the Story_Session's step unchanged, SHALL count no unresolved answer, and THE Gateway SHALL raise the Parent_Alert or Deferred_Question that decision requires. ON the **turn** path that record is appended by the Voice_Brain, once per turn whose spoken text was the word narration; ON the **routine** path it is appended by the Routine_Scheduler, which appends **both** a `routine` record and a `word` record when the `morning` behaviour published its `say` and that `say`'s narration was the word narration rather than the Requirement 5.4b greeting.

### Requirement 6: Consent records

**User Story:** As a parent, I want nothing adult-provided stored without my recorded consent, so that the robot never holds something I did not agree to.

#### Acceptance Criteria

1. THE Gateway SHALL define a Consent_Store interface over Consent_Records holding `consent_id`, `household_id`, `user_id`, `purpose`, `version`, `verification_method`, `given_at` and `withdrawn_at`, and SHALL implement it in memory. (C1.)
2. THE Consent_Store SHALL refuse a record whose `purpose` is outside the frozen shared `CONSENT_PURPOSES` list, whose `version` is empty, or whose `verification_method` is outside the frozen shared `VERIFICATION_METHODS` list, naming the field and echoing no value. (C36: both lists become runtime arrays with their unions derived from them, because a store cannot test membership against a type.)
3. WHEN a Consent_Record is withdrawn, THE Consent_Store SHALL set its `withdrawn_at` and SHALL keep the record, so that withdrawal is auditable. (safety.md §2.)
4. THE Consent_Store SHALL hold no name, no contact detail and no identity document; `user_id` and `household_id` are opaque ids. (safety.md §7.)
5. THE Gateway SHALL treat a Consent_Record with a non-null `withdrawn_at` as absent for every permission check.
6. THE Consent_Store SHALL be reachable from the Operator_Surface through one write route, `POST /v1/grandma/consent` (Requirement 16.2), because without it nothing in this phase can create a Consent_Record at all: Requirement 7.3 refuses every recording whose `consent_record_id` does not name a live `grandma_recording` record, so the console's add-recording control could only ever produce `no_consent` and the Grandma Done-when could not be demonstrated. THAT route SHALL sit behind the **unchanged** Phase 1.2 request guard and the same off-by-default Content_Admin_Argument as every other write, SHALL take `{ purpose, version, verification_method }` only, and SHALL resolve the `household_id` and the `user_id` **server-side** — from `householdForDevice(device_id, registry)` and from `DEV_USER_ID` respectively — refusing a body that names either (Requirement 7.9).
7. **A Consent_Record captured from an internal loopback console is NOT verifiable parental consent under the DPDP Act, and nothing in this phase may imply that it is.** `safety.md` §2 requires verifiable consent from an identifiable adult parent — reliable identity details or a virtual token, a plain-language notice, withdrawal as easy as giving, and erasure on withdrawal. What Phase 4 records is the **shape** of a consent record — who, what, when, version, verification method — against a single in-process dev user id, on an unauthenticated loopback surface with no parent, no identity and no notice (F7). Real verifiable consent arrives in Phase 5 with the backend, the role model and the parent app. THEREFORE no requirement, no code comment, no console label and no report sentence SHALL state or imply that `safety.md` §2 is satisfied by this phase; the Admin_Console's add-consent control SHALL be labelled as a developer control that records a consent **record**, and the README's content-admin section SHALL say the same (Requirement 20.9).

(C36.)
7a. THE Grandma_Store SHALL additionally run `checkOutput` on the **playback narration built from the submitted `title`**, for every Age_Stage whose template names the title and in **both** Supported_Langs, and SHALL refuse a title whose narration is refused, with reason `gate_refused` and the refusing rule, Age_Stage and language — so a title that cannot be spoken is never stored. The Content_Gate covers Content_Items only (C7), and a Grandma title is operator-submitted free text that goes straight into spoken narration: "Nani's doctor story" or "Blood Moon lullaby" would otherwise be stored, scheduled, and then silently unplayable. `gate_refused` SHALL be a member of `GRANDMA_REFUSALS`. THE `household_id` of a recording, a Consent_Record and a Grandma_Call SHALL come from `householdForDevice(device_id, registry)` — the C34 function, which answers the single `DEV_HOUSEHOLD_ID` constant for a registered device and null for anything else — and never from a request body: a `device_id` is bound to exactly one `household_id` (tech.md), and letting a caller name a household would be a cross-household write surface. THE Device_Registry SHALL NOT be changed to carry a household. A request body naming a `household_id` SHALL be refused, and WHERE `householdForDevice` answers null THE route SHALL refuse naming the `device_id` field and SHALL change nothing.
9a. THE `recorded_by_user_id`, the `requested_by_user_id` and the `user_id` of **every** Phase 4 write SHALL come from `DEV_USER_ID` — one in-process constant declared beside `DEV_HOUSEHOLD_ID` in `services/gateway/src/grandma/household.ts` — and a request body naming any of the three SHALL be refused `unrecognized_keys` on that path, exactly as a body naming a `household_id` is. The Gateway has no user model and this phase adds none: letting a loopback write name a user would let it attribute an adult's consent, a recording or a call to an arbitrary id, which is the same cross-tenant write surface C34 rejected for the household. `GrandmaCalls.apply(device_id, op, by)` takes its `by` from that constant, bound in the composition root. Phase 5 replaces it with the real user under RLS.
10. THE Grandma_Store SHALL set `media_handle` itself, from the `asset_id`, and SHALL refuse a request that submits one, so no caller can point a recording at anything. (C11.)
11. EVERY store-level refusal in Requirements 6 and 7 SHALL use the store-level code `invalid_field` with the offending field path, and THE route SHALL map it onto the single existing wire code of Requirement 16.4a. The two are deliberately different names for two layers; no new wire code is added for a field refusal.

### Requirement 10: Routines (XL-C02)

**User Story:** As a parent, I want the day to have a shape, so that mornings, meals and bedtime happen without a fight.

#### Acceptance Criteria

1. THE Gateway SHALL define a Routine_Store interface over Routines holding `routine_id`, `name`, `at` (`HH:MM` local), `enabled` and a Routine_Behaviour id, SHALL implement it in memory seeded from the Starter_Content's routine templates, and SHALL seed at least `morning`, `brushing`, `meals`, `play time`, `wind down` and `bedtime` with the times Phase 2.2 Requirement 13.2 draws.
1a. THE six routine times SHALL have exactly **one** source of truth after this phase, and the choice is the single-source one: `ROUTINE_FIXTURE`, `RoutineFixture` and `createRoutines` are **deleted** from `services/gateway/src/brain/tools/routines.ts`, which keeps only the `Routines` interface and the `RoutineLookup` type, and all **seven** `createRoutines(` call sites move to `createRoutineStore` (task 7.5 names them). Left alone, production would answer `routine_lookup` from the Starter_Content templates while `routine_lookup`'s own tests kept exercising a fixture with its own copy of the same six rows and nothing asserted the two agree — the two-sources-of-truth risk Requirement 19.5 solves on the parent-app side and which must not be left open here. So `createRoutineStore` takes an optional `playMinutes` seed as well as its `seed`, because six of the seven call sites are tests that pass a per-device play-minute total today, and `RoutineStore extends Routines` means one object still satisfies both `routine_lookup`'s dependency and the Device_Policy_Gate's `playMinutesUsed` read. `services/gateway/src/brain/tools/device-action.ts` is still **not** edited.
2. THE Routine_Behaviour of each seeded Routine SHALL be an ordered list of at most the design's cap of device actions, each one of `say`, `animate`, `gesture`, `led` and `play` only, and EVERY action SHALL carry the exact `data` object the design's behaviour payload table gives it, built from the named constants there. (C16.) NO Phase 4 behaviour sends `play`: both `PLAY_SOURCES` values (`stream`, `cache`) promise audio the Gateway cannot serve this phase (C30), so `play` stays in the allowed set and is used by nothing. THE contract's `data` objects are strict with every field required, so a behaviour with an invented, missing or extra key is a schema failure at the sender — which is why the table is exhaustive rather than illustrative.
3. WHEN a Routine's time becomes due on the Clock, THE Routine_Scheduler SHALL ask the Device_Policy_Gate to send each action of its Routine_Behaviour in order, and SHALL stop at the first refusal.
4. IF the Device_Policy_Gate refuses an action, THEN THE Gateway SHALL send that action and every later action of that behaviour not at all, SHALL add one `routine_fired` Log_Entry carrying the Policy_Refusal and the counts of actions sent and refused, and SHALL not retry that occurrence. (C16, C19.)
4a. IF the command **sender** fails for an action the Device_Policy_Gate allowed — `DeviceActions.request` answering `{ outcome: "error" }` because the device is offline or the broker is disconnected, which is not a policy refusal and for which `policyRefusal` reports null — THEN THE Gateway SHALL stop the behaviour at that action, SHALL send nothing further, SHALL count that action in the entry's `refused` with `refusal: null`, SHALL add the `routine_fired` or `grandma_event` entry, SHALL retry nothing, and SHALL accrue play minutes **only when at least one action was actually published**. A send failure is therefore distinguishable in the log from a policy refusal by `refusal` being null while `refused` is non-zero, and no `PolicyRefusal` value is invented for it. (Property 6 is scoped to a sender that accepts every allowed action; this requirement is the rule for the sender that does not.)
5. WHEN a Routine's action receives a `rejected` or `failed` ack, THE Gateway SHALL treat the ack `reason` as final and SHALL send no replacement command. (safety.md §5.)
6. THE Routine_Scheduler SHALL fire each enabled Routine at most once per local day, SHALL fire nothing for a disabled Routine, and SHALL schedule every due time on the Deadlines. (C15.)
7. WHEN a Routine_Behaviour completes with at least one action sent, THE Gateway SHALL add one Activity_Record of kind `routine` naming that `routine_id`.
8. EVERY `say` in a Routine_Behaviour SHALL carry narration built from a fixed per-language template that passes `checkOutput` for the active Child_Context's Age_Stage before the command is sent.
9. THE Routine_Scheduler SHALL survive a Routine being added, disabled or re-timed between firings, and SHALL re-compute the next due time from the Clock rather than from a stored countdown.
10. A Routine SHALL be due on a tick when it is enabled, has not fired on the current Local_Day_Key, and its `at` in local minutes falls in the Catch_Up_Window ending at the tick's local minute — so a tick a minute late still fires it, and a Routine enabled or re-timed to a time earlier than the window does **not** fire retroactively. The same rule decides a Grandma_Schedule. (Req 8.7, 10.6.)
11. THE Routine_Scheduler SHALL take the Age_Stage, the languages and the device policy for a scheduled behaviour from the **existing** Child_Context table's `forDevice(device_id)` — the same source the Device_Policy_Gate reads — so a routine and a turn cannot disagree about who is listening. WHERE no child is active, `forDevice` returns `MOST_RESTRICTIVE_CONTEXT`, which opens no content category and has movement off, and the behaviour is built and gated against that.
12. THE Routine_Scheduler SHALL read the specific Policy_Refusal through the Device_Policy_Gate's existing `policyRefusal(device_id, action)` and SHALL send through its existing `request(device_id, …)`; neither function's signature, behaviour nor refusal order SHALL change, because `request` deliberately returns the opaque `policy` reason and the log needs the enum. (C16; Phase 3 `device-action.ts` unchanged.)
13. THE Routine_Scheduler SHALL take its device list as an injected Scheduler_Devices function from the composition root, which answers the configured `device_id` when the Device_Registry reports it registered and `helloSeen`, and an empty list otherwise; and SHALL fire nothing and add no Log_Entry for any device not in that list. THE Device_Registry SHALL NOT gain an enumeration member: it exposes per-device predicates only, `createRegistry` takes exactly one device, and Phase 4 registers exactly one — so the list is a composition-root concern, not a Registry change.

### Requirement 11: Charge reminders (XL-C05)

**User Story:** As a parent, I want to know when the robot is hungry, so that it is charged when my child wants it.

#### Acceptance Criteria

1. WHEN the Gateway accepts a `status` message, THE Charge_Reminder component SHALL read that message's `battery_pct` and `charging` and SHALL decide whether a reminder is due. (C17.)
2. THE Charge_Reminder thresholds SHALL be exactly 20% and 10%, exported as one frozen shared constant.
3. WHEN the battery crosses from above a threshold to at or below it, THE Charge_Reminder SHALL fire that threshold's behaviour exactly once through the Device_Policy_Gate, and SHALL not fire it again while the battery stays at or below it. (C17.)
4. WHEN the battery rises above a threshold by at least the design's hysteresis margin, or `charging` becomes true, THE Charge_Reminder SHALL re-arm that threshold.
5. THE 20% behaviour SHALL carry exactly one movement-bearing action — one `gesture` — and THE 10% behaviour SHALL request none, so that a nearly flat robot is never asked to move. (safety.md §5; C37, which is also what gives Requirement 12.7's movement-off case for a charge reminder something real to refuse.)
6. IF the Device_Policy_Gate refuses a reminder, THEN THE Gateway SHALL send nothing, SHALL add one `routine_fired` Log_Entry with trigger `battery`, the threshold and the Policy_Refusal, and SHALL leave the threshold fired so that quiet hours do not queue a reminder for later. (C19.)
7. THE Gateway SHALL add one `routine_fired` Log_Entry per reminder, carrying the trigger, the threshold, the `battery_pct` and the counts, and SHALL lose the armed state on restart.
8. THE Charge_Reminder SHALL read the battery only from an accepted `status` message and SHALL invent no value when none has arrived. (Document B; C29.)
9. ON the **first** accepted `status` for a device, THE Charge_Reminder SHALL arm a threshold only if that status is at or above `threshold + the hysteresis margin` or reports `charging` true, and SHALL otherwise leave it unarmed and fire nothing. A device first seen at 18% therefore gets no reminder until it is charged above the margin and falls again: a first reading is not a crossing, and nagging about a battery the cloud has never seen full is the less conservative choice. (C17, Property 7.)
10. WHERE the battery reading handed to the Charge_Reminder is absent or outside 0–100, THE Charge_Reminder SHALL treat that reading as absent, SHALL change no armed flag and SHALL fire nothing. **This is a defensive branch, not a reachable wire case**, and is stated as one: `packages/shared/src/gateway-contract/status.ts` declares `battery_pct: pct` and `charging: z.boolean()` as **required**, so an accepted `status` always carries both and always in range. The branch exists because `ChargeReminders.onStatus(deviceId, batteryPct, charging)` is a plain function that the composition root, a test or a later internal `StatusMemory` read can call with anything, and a total function is cheaper than an argument nobody re-validates. A test SHALL exercise it by calling the function directly rather than by building an invalid `status` message, which the contract would reject first.

**User Story:** As a parent, I want play to end kindly, so that the limit is not a punishment.

#### Acceptance Criteria

1. THE Routine_Store SHALL accumulate play minutes per device per Local_Day_Key and SHALL expose them as the existing `playMinutesUsed` the Device_Policy_Gate already reads, with no change to that function's signature. The accrual sources SHALL be exactly these three, and nothing else:
   - **a completed turn**: the whole minutes of Clock time from the turn's accepted `audio_start` to its reply ending, rounded up to a minimum of one minute. The `audio_start` instant travels on the turn as `ReplyTarget.audioStartMs`, captured by the Audio_Turn where the accepted `audio_start` is handled (C35); the Voice_Brain calls Play_Accrual once per turn that reached its reply ending, with `Math.max(1, Math.ceil(elapsedMs / 60_000))`.
   - **a Routine_Behaviour that sent at least one action**: one minute, from the Routine_Scheduler;
   - **a Grandma playback that sent at least one action**: the recording's `duration_s` in whole minutes, rounded up, from the Routine_Scheduler.

   A refused behaviour, a refused turn and a Safe_Redirect accrue nothing, so a child is never charged play time for something the robot did not do.
2. WHEN a Play_Accrual would take the day's accumulated play minutes from below the active Child_Context's `playLimitMinutes` to at or above it, THE Play_Accrual SHALL request the Nap_Sequence **before** it records the minutes, and SHALL then record them; and THE Nap_Sequence SHALL be requested at most once per Local_Day_Key. (C18.) THE Device_Policy_Gate SHALL NOT be changed, exempted or bypassed for the nap: it is reached while `playMinutesUsed` still reports the pre-accrual total, so the gate allows the nap on its own unchanged rule and refuses every ordinary behaviour from the moment the ledger closes. WHERE an accrual lands at or above the limit without crossing it — because the limit was already reached — THE Play_Accrual SHALL request no Nap_Sequence.
3. THE Nap_Sequence SHALL be, in order, one `say` with a per-language, per-Age_Stage nap narration that passes `checkOutput`, one `animate` with a sleepy expression, and one `led` set to a dim `solid`, each with the exact `data` the design's behaviour payload table gives it. (C18.)
4. IF the Device_Policy_Gate refuses a Nap_Sequence action for any reason other than `play_limit` — quiet hours, or `movement_off` for an action the nap does not in fact carry — THEN THE Gateway SHALL stop the sequence at that action, SHALL send nothing further, and SHALL add one `routine_fired` Log_Entry with trigger `play_limit` and the Policy_Refusal. (C19: a nap inside quiet hours is silence, which is the open ruling F3, not a defect of this requirement.)
5. WHEN the local day rolls over on the Clock, THE Routine_Store SHALL reset the day's play minutes and the Nap_Sequence's once-per-day mark.
5a. THE Routine_Scheduler's tick SHALL NOT fire a Nap_Sequence of its own, and THE Routine_Scheduler SHALL expose **no** play-minutes notification member at all. The limit is reached by an accrual and by nothing else, so a tick that found the limit already reached could only ever send a nap the gate refuses `play_limit` — the dead path Requirement 13.2 exists to avoid. The one direction of travel is the other way: the scheduler supplies `fireNap(device_id)` to Play_Accrual, Play_Accrual decides the crossing, and nothing is reported back. An earlier draft put an `onPlayMinutes` member on the scheduler that re-read nothing and decided nothing; a member with no specified behaviour is a member to delete, so it is deleted. The tick fires routines and Grandma schedules only.
6. WHERE the active Child_Context has no Play_Limit, THE Routine_Scheduler SHALL fire no Nap_Sequence and THE Device_Policy_Gate SHALL refuse nothing for a play limit.
7. THE Gateway SHALL add one Activity_Record of kind `play` carrying the window's minutes, and SHALL carry no transcript and no content text on it.

### Requirement 14: Activity records and reports (XL-C08)

**User Story:** As a parent, I want a summary I asked for of what my child did, so that I can care for them better — and nothing more than that.

#### Acceptance Criteria

1. (C1.)
2. THE Activity_Record kinds SHALL be exactly `turn`, `story`, `word`, `routine`, `play` and `cry`, exported as one frozen shared constant.
3. THE Activity_Store SHALL hold no transcript, no reply text, no content text, no title, no child name, no `active_child_id` and no audio value; `categories` SHALL hold only values from `CONTENT_CATEGORIES`, which are content metadata and name no child. (safety.md §1, §7; C20.)
4. THE Shared_Package SHALL export one pure `summariseActivity(records, window)` returning a Report_Summary carrying the `window` it was given plus exactly these eight counts and no other field — nine members in all — each defined here so the Gateway, the console and the app cannot read them differently: (C21.)
   - `turns`: the number of `turn` records;
   - `play_minutes`: the sum of `minutes` over `play` records, with a null `minutes` counted as 0;
   - `play_sessions`: the number of `play` records;
   - `routines_completed`: the number of `routine` records;
   - `stories_heard`: the number of `story` records, **not** de-duplicated by `ref_id`, because hearing the same story twice is two listens and de-duplicating would be the start of a preference;
   - `words_learned`: the number of `word` records, likewise not de-duplicated;
   - `cry_moments`: the number of `cry` records;
   - `categories_heard`: the union of every record's `categories`, de-duplicated, sorted by the order of `CONTENT_CATEGORIES` so the list is deterministic and carries no frequency, weight or rank.

6. THE Gateway SHALL compute a Report_Summary only when a report is requested, SHALL compute nothing continuously in the background, and SHALL store no computed summary as a profile. (C20.)
7. WHEN a report is requested, THE Gateway SHALL add one `report_built` Log_Entry carrying the period, the window length in days and the counts, and no text.
8. THE `summariseActivity` function SHALL depend only on its two arguments, SHALL read no clock, SHALL perform no I/O, SHALL return the same summary for the same input and the same summary for any permutation of the records, and SHALL count exactly the records whose `at` satisfies `from <= at < to` — a **half-open** window, so two adjacent windows count each record once and never twice.
9. THE daily period SHALL be a window of exactly 24 hours and the weekly period one of exactly 7 × 24 hours, each with `to` the requested instant and `from` that instant less the period's length. A record at `to` exactly therefore falls in the *next* window, which is what 14.8's half-open rule means.
10. IF a record's `at` is not a parseable ISO instant, THEN `summariseActivity` SHALL exclude it from every count and SHALL throw nothing: a report is a read of whatever is held, and one bad row must not deny a parent their summary.

(Phase 1.2 Requirement 13.7, unchanged.)
4a. EVERY field refusal on EVERY new route SHALL answer **400 with the existing `invalid_fields` code, in the body shape the Operator_Surface already uses**, and SHALL echo no submitted value.
